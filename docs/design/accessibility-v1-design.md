# Accessibility v1 基本設計書

## 1. 目的

本書は、Yamabiko Table Reorder の Accessibility v1 Phase 1 について、利用者から見える Keyboard 操作、focus、支援技術からの認識、入力上の問題、並び替え結果の通知に関する振る舞いを定義する。

Accessibility v1 の要件は `docs/requirements/accessibility-v1-requirements.md` を正本とする。

RF 自体の画面、入力方法、並び替え条件、確認、反映中表示、完了通知、失敗時の振る舞いは `reorder-form-v1-design.md` および `reorder-v1-design.md` を正本とする。Accessibility の検討によって既存の RF 共通メッセージを改訂する場合は、改訂内容を `reorder-form-v1-design.md` にも反映し、RF 共通メッセージの正本は同書に維持する。

本書では、具体的な DOM 構造、ARIA 属性、使用する WordPress Component、React の state 管理、event 処理、内部 architecture、テスト実装方法は定義しない。

## 2. 基本方針

Accessibility v1 Phase 1 では、Reorder Form（RF）を Keyboard と支援技術から利用できる正式な並び替え経路として成立させる。

Row / Column DnD 自体へ Keyboard DnD を追加しない。

RF では可能な限りブラウザーおよび WordPress Editor が提供する標準的な Keyboard 操作を利用し、YTR 独自の Keyboard 操作体系を追加しない。

利用者が操作中に表示や状態が変化した場合も、次に何を操作できるか分かる位置へ focus を維持または移動する。

結果やエラーを知らせるためだけに、不必要な focus 移動は行わない。

視覚的なメッセージと支援技術への通知は、同じ内容を利用できる場合は共有する。ただし、それぞれに必要な情報量やタイミングが異なる場合は、同一の表示方法であることを必須としない。

Accessibility v1 Phase 1 で新しく追加する利用者向けメッセージは、本書の Basic Design で日本語と English の両方を定義する。既存 Reorder / RF Design ですでに定義済みのメッセージは既存設計を正本とする。Accessibility の観点から既存メッセージ自体を見直す場合も、本書で日本語 / English を明示したうえで、RF 共通メッセージは `reorder-form-v1-design.md` へ同じ内容を反映する。

## 3. Keyboard による RF 操作

### 3.1 RF の開始

利用者は WordPress Editor の標準的な Keyboard 操作によって対応 Table を選択し、Table toolbar の「フォームで並び替え」へ到達して RF を開始できる。

RF 専用の Keyboard shortcut は設けない。

RF を開始すると入力画面を表示し、利用者がそのまま Keyboard 操作を続けられる状態にする。

### 3.2 RF 内の移動

RF 内では、標準的な Keyboard 操作によって次の操作へ順番に到達できるようにする。

- 行 / 列の選択
- 移動元
- 移動先
- 上 / 下または左 / 右
- キャンセル
- 並び替え

Tab および Shift+Tab による移動、radio、select、number input、button などの各操作は、ブラウザーおよび WordPress が提供する標準的な Keyboard 操作に従う。

独自の矢印キー操作や Keyboard state machine は追加しない。

### 3.3 行 / 列の切り替え

行または列を選択した場合は、その選択操作に focus を残したまま入力フォームを切り替える。

フォームが切り替わったことだけを理由に、移動元入力など別の操作へ自動的に focus を移動しない。

利用者が次に Tab 操作を行った場合は、選択した方向に対応する最初の入力へ進めるようにする。

### 3.4 狭い表示での折りたたみ

狭い表示で RF を折りたたむ、または展開する操作は Keyboard から実行できるようにする。

折りたたみまたは展開後も focus はその操作に残し、表示変更によって操作位置を見失わないようにする。

RF の高さ調整や Popover の移動に対する Keyboard 代替は Phase 1 の対象外とする。

## 4. Focus の基本設計

### 4.1 RF を開いた場合

RF を toolbar から開始した場合は、RF 内の「行 / 列」を選択する操作へ focus を移す。

初期状態では「行」が選択されていることを利用者が認識できるようにする。

これにより、利用者は現在の並び替え方向を確認したうえで、そのまま入力操作へ進める。

### 4.2 RF を明示的に終了した場合

利用者が RF の「キャンセル」を実行した場合は、対象 Table が引き続き操作可能であれば、Table toolbar の「フォームで並び替え」へ focus を戻す。

RF toolbar 入口を再度操作して RF を閉じた場合は、その入口に focus を維持する。

### 4.3 別の操作対象へ移動したことによって RF が終了した場合

利用者が別の Table や別の Editor 操作へ移動したことによって RF が終了した場合は、古い Table の RF 入口へ focus を戻さない。

利用者が新しく移動した操作位置を優先し、YTR が focus を奪わないようにする。

### 4.4 表示形式が変化した場合

RF を開いている途中で表示領域が変化し、Popover 表示と画面下部表示が切り替わった場合も、現在操作している入力または操作に focus を維持する。

ソフトウェアキーボードの表示などによって利用可能な表示領域が変化した場合も、入力中であることだけを理由に focus を別の操作へ移動しない。

## 5. 操作部品と状態の認識

RF の主要な操作について、支援技術を利用する利用者がその目的と状態を認識できるようにする。

最低限、次を認識できるようにする。

| 操作 | 認識できる内容 |
| --- | --- |
| RF toolbar 入口 | フォームを使って並び替える操作であること |
| 行 / 列 | 並び替える方向と現在選択されている方向 |
| 移動元 | 移動する行または列を指定する操作であること |
| 移動先 | 移動先の行または列を指定する操作であること |
| 上 / 下 | 移動先行との位置関係 |
| 左 / 右 | 移動先列との位置関係 |
| 並び替え | 現在の指定で並び替えを開始する操作であること、および実行可能かどうか |
| キャンセル | Table を変更せず RF を終了する操作であること |
| 折りたたみ / 展開 | RF の現在の表示状態と、次に行う表示変更 |

行番号入力では、現在入力できる範囲についての案内を支援技術からも確認できるようにする。

列の選択では、列番号だけでなく、利用可能な場合は既存の列見出しも含めて列を識別できるようにする。

## 6. 入力上の問題

### 6.1 初期状態と未入力

RF を開いた直後の未入力または未選択の状態は、エラーとして通知しない。

必要な指定が揃っていない間は「並び替え」を実行できない状態とし、各入力の意味と有効な入力条件から、利用者が必要な指定を確認できるようにする。

### 6.2 行番号が有効でない場合

行番号に、有効範囲外の値や整数として扱えない値が入力された場合は、該当する入力に修正が必要であることを支援技術から認識できるようにする。

有効な行番号の範囲についての案内を、その入力に対する修正情報として確認できるようにする。この案内には既存 RF Design の行番号範囲メッセージを利用し、Accessibility 専用の別文言は追加しない。

入力中に問題が判明しただけでは focus を移動しない。

利用者は現在の入力位置に留まったまま値を修正できるようにする。

### 6.3 列の選択が現在有効でなくなった場合

Table の変更などによって、それまで選択していた列が現在の選択肢として成立しなくなった場合は、その選択が改めて必要であることを認識できるようにする。

該当する移動元または移動先の列選択には、次のメッセージを表示し、支援技術からも確認できるようにする。

| 言語 | メッセージ |
| --- | --- |
| 日本語 | 選択していた列は現在利用できません。列をもう一度選択してください。 |
| English | The selected column is no longer available. Select a column again. |

移動元と移動先の両方が現在有効でない場合は、それぞれの入力に同じメッセージを関連付ける。入力の識別は各入力自身の名称によって行い、移動元用 / 移動先用に別文言は設けない。

この場合も、問題を知らせることだけを理由に別の操作へ focus を移動しない。

### 6.4 Table 構造上移動できない場合

必要な入力がすべて成立した後、結合セルなど Table の構造によって移動できないことが判明した場合は、既存 RF 設計で表示する移動不可理由を支援技術からも認識できるようにする。

この状態は特定の一入力だけのエラーとして扱わず、現在の指定全体に対する結果として知らせる。

利用者が指定を変更した場合は、以前の理由を終了し、新しい指定に対応する現在の結果だけを知らせる。

### 6.5 並び順が変わらない場合

現在の指定では並び順が変化しないことが判明した場合は、既存 RF 設計の案内を支援技術からも認識できるようにする。

focus は現在の操作位置に維持する。

## 7. 反映前の確認

並び替えの反映に時間がかかる可能性があり、確認画面を表示する場合は、focus を RF から確認画面の「続行」へ移す。

確認画面では、利用者が確認内容、移動内容、「続行」「キャンセル」の選択肢を Keyboard と支援技術から確認できるようにする。

確認画面を表示している間は focus が確認画面の外へ意図せず移動しないようにする。

### 7.1 続行

利用者が「続行」を選択した場合は反映へ進む。

確認画面を終了した後は、対象 Table の反映中状態を示す位置へ focus を移し、反映が完了または失敗するまで操作位置を失わないようにする。

反映が短時間で完了し、反映中の位置への移動を利用者が認識する前に結果が確定した場合は、成功または失敗に対応する最終的な focus 移動先へ直接移ってよい。

### 7.2 キャンセル

利用者が確認をキャンセルした場合は Table を変更せず、入力内容を保持した RF へ戻る。

focus は RF の「並び替え」操作へ戻し、そのまま再実行または入力修正を行えるようにする。

## 8. 反映中

反映中表示が現れた場合は、利用者が対象 Table の並び替え処理中であることを Keyboard および支援技術から認識できるようにする。

反映中は、対象 Table の反映中状態を示す位置に focus を維持する。対象 Table の一時的な非表示や再表示が発生しても、Table 内の消失するセルや編集位置へ focus を残さない。

反映処理中の対象 Table へ誤って操作を続けられる状態にはしない。

対象 Table 以外の Editor 全体を不必要に操作不能にはしない。

反映完了後は 9 節、失敗後は 10 節の復帰先へ focus を移す。

## 9. 並び替え成功後の Focus

正常に並び替えが完了した場合は、RF を終了する。

その後、移動した結果を利用者が確認できる位置へ表示を戻し、次の位置へ focus を移す。

- 行を移動した場合は、移動後の行を確認できるセル
- 列を移動した場合は、移動後の列を確認できるセル

focus を移したセルは、通常のセル編集を意図せず開始するためのものではなく、並び替え結果を確認するための位置として扱う。

移動後の正確な位置を確認できない場合に、隣接する別の行や列を並び替え結果として推測して focus しない。

対象 Table 自体は存在している場合は、利用者がその Table から操作を継続できる安定した位置を復帰先とする。

対象 Table が既に存在しない場合は、存在しない Table へ focus を戻そうとせず、現在の Editor 操作位置を優先する。

## 10. 並び替え失敗後の Focus

並び替えを完了できなかった場合は、既存 RF 設計に従って入力内容を保持した RF へ戻る。

現在の指定がそのまま再実行可能である場合は、「並び替え」操作へ focus を戻す。

行番号や列の選択など、入力自体に修正が必要な場合は、現在選択している行または列のフォーム内で、通常の Keyboard 操作順に見て最初に修正が必要な入力へ focus を移す。

入力自体は有効でも、現在の指定が no-op、結合セルによる移動不可、または現在の Table では続行できない状態になっている場合は、現在選択している方向の「移動する行」または「移動する列」へ focus を戻し、そこから指定を見直せるようにする。

失敗通知を表示することだけを目的として focus を通知表示へ移動しない。

## 11. 支援技術への結果通知

### 11.1 基本方針

視覚的な Notice やメッセージだけに依存せず、操作結果を支援技術から認識できるようにする。

結果通知は focus 移動とは独立して行い、通知を聞かせるためだけに利用者の操作位置を変更しない。

同じ結果を画面の再表示などによって繰り返し通知しない。

利用者の指定または結果が変化した場合だけ、新しい内容として通知する。

既存 RF Design で日本語と English が定義済みの移動不可理由、並び順が変わらない案内などは、その既存文言を支援技術への通知にも利用する。Accessibility v1 Phase 1 で新規追加する文言は、6.3 節の列再選択メッセージと、並び替え成功時に移動内容を具体的に知らせる announcement とする。Accessibility の観点から改訂する既存文言は 11.6 節で整理する。

### 11.2 並び替え成功

並び替えと表示復帰が完了した時点で、並び替えが成功したことを一度だけ知らせる。

画面上の短い完了通知は、既存 RF Design の「並び替えが完了しました。 / Reordering complete.」を引き続き利用する。

支援技術向けには、並び替え前の移動元位置と、並び替え後に移動対象が配置された位置を含む次の announcement を使用する。

| 移動 | 日本語 | English |
| --- | --- | --- |
| 行 | `{移動元}行目を{反映後位置}行目の位置へ移動しました。` | `Moved row {source} to position {destination}.` |
| 列 | `{移動元}列目を{反映後位置}列目の位置へ移動しました。` | `Moved column {source} to position {destination}.` |

ここで「移動元」は並び替え前の 1-based 位置、「反映後位置」は並び替え完了後に移動対象が配置された 1-based 位置を表す。RF で指定した「移動先の行 / 列」の番号は、並び替え後に別の位置を指す場合があるため、成功 announcement では使用しない。

たとえば、並び替え前の3行目を移動し、完了後にその行が5行目へ配置された場合は、次のように知らせる。

| 言語 | announcement |
| --- | --- |
| 日本語 | 3行目を5行目の位置へ移動しました。 |
| English | Moved row 3 to position 5. |

視覚通知と支援技術向け announcement が完全に同じ文言であることは必須としない。

### 11.3 並び替え失敗

反映を完了できなかった場合は、Table が変更されていないことを含め、次のメッセージを画面上と支援技術の両方へ知らせる。

| 言語 | メッセージ |
| --- | --- |
| 日本語 | 並び替えを完了できませんでした。テーブルは変更されていません。 |
| English | The reorder could not be completed. The table was not changed. |

「失敗」という抽象的な結果だけではなく、並び替えを完了できなかったことと、Table が変更されていないことを利用者が判断できる文言とする。

### 11.4 Table 構造上移動できない場合

結合セルなどによって移動できない場合は、既存 RF Design で日本語と English が定義されている移動不可理由を支援技術からも知らせる。

Accessibility 用に別の移動不可メッセージは追加しない。

指定を変更して別の理由へ変化した場合は、新しい理由だけを知らせる。

### 11.5 並び順が変わらない場合

現在の指定では並び順が変わらない場合は、既存 RF Design で定義されている案内を、その状態が新しく成立した時点で支援技術からも知らせる。

Accessibility 用に別の no-op メッセージは追加しない。

### 11.6 既存メッセージの見直し

Accessibility v1 Phase 1 では、既存メッセージのうち、記号だけでは意味を認識しにくい確認内容と、結果が抽象的な失敗メッセージを見直す。改訂後の RF 共通表示メッセージは `reorder-form-v1-design.md` にも同じ内容を反映し、同書を正本とする。

反映に時間がかかる可能性がある場合の確認画面では、移動内容を `→` の記号だけで示さず、行または列と反映後の位置を文章で示す。

| 用途 | 日本語 | English |
| --- | --- | --- |
| 行の移動内容 | `{移動元}行目を{反映後位置}行目の位置へ移動します。` | `Move row {source} to position {destination}.` |
| 列の移動内容 | `{移動元}列目を{反映後位置}列目の位置へ移動します。` | `Move column {source} to position {destination}.` |

ここで「反映後位置」は、並び替え完了後に移動対象が配置される 1-based の位置を表す。RF で指定した「移動先の行 / 列」と同じ番号であるとは限らないため、「移動先行」「移動先列」という表現にはしない。

たとえば、2行目が反映後の5行目になる確認では、次のように表示する。

| 言語 | メッセージ |
| --- | --- |
| 日本語 | 2行目を5行目の位置へ移動します。 |
| English | Move row 2 to position 5. |

失敗メッセージは 11.3 節の文言へ改訂し、従来の `Reordering failed. The table has not been changed.` / 「並び替えが失敗しました。テーブルは変更されていません。」は使用しない。

`Apply the new order? / 並び替えを反映しますか？`、反映に時間がかかることを知らせる案内、反映中メッセージ、完了通知、結合セルによる移動不可理由、no-op、および現在の Table で継続できない案内は、現行文言を維持する。

## 12. Wide / Narrow 表示の共通性

Popover 表示と画面下部表示のどちらでも、Keyboard 操作、入力の意味、focus の基本ルール、支援技術から取得できる情報を同じものとする。

表示形式が変わったことによって、同じ RF 操作の意味や Keyboard 操作順序を別物にしない。

Phase 1 では、Popover のドラッグ移動および高さ調整そのものに対する Keyboard 代替は要求しない。

## 13. Phase 1 対象外

本設計では次を対象外とする。

- Row DnD 自体の Keyboard DnD
- Column DnD 自体の Keyboard DnD
- RF Popover のドラッグ移動に対する Keyboard 代替
- RF 高さ調整に対する Keyboard 代替
- RF 独自 Keyboard shortcut
- Target Size の全面監査
- contrast の全面監査
- zoom / reflow の全面監査
- motion の全面監査
- WCAG 2.2 AA 全項目の完全監査
- 複数 screen reader / OS 組み合わせの網羅検証
- screen reader ごとの専用動作
- WordPress Core Component 自体のアクセシビリティ問題の独自修正

これらは親 Issue #1046 の後続 Phase で必要性を評価する。
